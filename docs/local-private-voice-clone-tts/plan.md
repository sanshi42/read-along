# 本地私有声音克隆 TTS Plan

## 方案

### 同机 A/B 评测

- 为 CosyVoice3 与 Qwen3-TTS 分别创建位于系统临时目录的隔离环境；模型权重、上游源码、生成样本和测量结果均不进入工作区。
- 两个模型使用同一个 12 秒、24kHz、单声道 PCM 参考 WAV、同一份准确逐字稿、同一组测试文本和相同目标 WAV 格式。
- 评测语料包含 8–12 句真实中文阅读文本，覆盖长句、数字、日期、百分比、中文标点、中英混读、多音字和专有名词。
- 模型支持随机种子时固定并记录种子；模型无法保证确定性时记录限制，不把跨实现的伪确定性作为公平性前提。
- 每个模型记录安装版本、模型 revision、运行参数和 Apple Silicon 兼容补丁，确保结论可以解释和复查。

### 自动指标与稳定性

- 使用本机 SenseVoice 回转录生成音频，计算字符错误率，并单独核对数字、日期、英文词和专有名词等关键实体。
- 分别测量环境就绪后的模型冷启动时间、首句完成时间、预热后实时率（RTF）和进程峰值常驻内存。
- 每个模型连续生成至少 20 句，检查进程崩溃、音频截断、异常重复、空输出和持续内存增长。
- 自动测量只负责筛除不满足运行门槛或存在明显可靠性问题的候选，不用单一分数代替人工听感。

### 匿名人工盲测

- 为两模型生成内容一一对应的匿名 A/B 样本，并随机交换每组样本的模型顺序。
- 随机映射单独保存；盲测页面或清单不显示模型名、文件路径特征和运行指标。
- 用户按自然度、音色相似度和稳定性评价，完成评分后再揭示映射。
- 若只有一个候选能生成有效样本，则不伪造 A/B 比较，改为对该候选进行隐藏模型身份的接受度听测；若没有候选能生成有效样本，则直接记录失败证据。

### 胜出规则

1. 淘汰无法在 M4、16GB MacBook Pro 上稳定运行，或预热后持续生成 `RTF > 1` 的模型。
2. 淘汰出现明显截断、重复、空输出，或人工排除 SenseVoice 自身识别错误后总 CER 超过 5%，或至少有两个关键实体错读的模型。
3. 对剩余候选，以用户盲测的自然度和音色相似度为主要决策依据，自动指标用于解释和处理接近结果。
4. 若两个候选均不合格，保持 Kokoro 为当前默认后端，记录结论并结束 Topic，不实施声音克隆集成。

### 隔离环境与兼容性顺序

- CosyVoice3 使用独立 Python 3.10 环境，按 [官方仓库](https://github.com/FunAudioLLM/CosyVoice) 递归克隆并安装；固定实际 Git commit 和模型 revision 后再运行。Linux x86_64 专用的 `ttsfrd` wheel 不在 macOS 安装，使用官方默认 WeTextProcessing 路径。
- Qwen3-TTS 使用独立 Python 3.12 环境，按 [官方仓库](https://github.com/QwenLM/Qwen3-TTS) 安装 `qwen-tts`；使用 `Qwen/Qwen3-TTS-12Hz-0.6B-Base`，不安装 CUDA 专用 FlashAttention。
- 每个候选先尝试官方 PyTorch 实现的 MPS 路径；若上游算子不支持 MPS，再在同一官方实现中尝试 CPU。仅允许为 Apple Silicon 兼容性修改临时 checkout，并把完整 diff 写入 `run.json`。
- 第一轮不换用第三方 MLX 移植、量化模型或不同 checkpoint，因为这会同时改变运行时和模型，破坏同模型公平比较。若两个官方实现均不合格，另开后续 Topic 评估原生移植方案。
- 两个模型不同时驻留；一个模型的连续生成和内存测量结束后退出进程，再启动另一个模型。

### 统一运行协议

- 随机种子固定为 `20260702`；上游不支持完整确定性时记录实际可控的 Python、NumPy 和 PyTorch 种子及限制。
- 每个模型进程先完成一次不计分预热，再按相同顺序生成十条评分语料；稳定性阶段按正序和倒序各生成一次，共 20 句。
- 生成耗时从调用模型合成接口前开始，到模型返回完整波形时结束；音频格式转换时间不计入模型 RTF。
- RTF 使用“生成耗时 ÷ 生成音频时长”，报告预热后十条评分语料的中位数、P95 和最大值。
- 冷启动从启动模型进程开始，到模型可接受首个合成请求为止；首句时间从冷进程启动到第一条完整 WAV 落盘为止。
- `/usr/bin/time -l` 记录整个模型进程峰值 RSS，同时每次生成后采集 RSS，以识别连续增长。
- 原始输出保留用于诊断；盲测副本统一转换为 PCM 16-bit、24kHz、单声道 WAV，转换后再次验证时长和可解码性。

- `summarize.py` 对规范化后的中文文本计算总 CER，并把数字、日期、百分比、英文词和专有名词逐项列为关键实体；SenseVoice 错误必须经人工听辨复核后才计入 TTS 淘汰证据。

### 阶段门禁

- 评测夹具先用两个确定性假 runner 验证计时、RTF、CER、错误记录和匿名映射，再接真实模型，避免把夹具错误误判为模型问题。
- 每个真实模型先生成一条 smoke sample；只有输出可解码且内容基本正确，才执行完整十句和连续 20 句评测。
- T005 形成胜出结论后，才能细化 T006–T008 的文件级实现计划。该计划必须基于胜出模型的真实加载 API、依赖版本和兼容补丁，不能预先假设两个模型共用同一运行时。

## 声音档案

- 评测阶段直接使用系统临时目录中的授权参考片段，不复制课程完整音频。
- 存在胜出模型后，在 `READ_ALONG_HOME` 下建立私有的单一全局声音档案目录，保存 `voice-profile.json` 和稳定参考 WAV；两者不位于项目仓库。
- `voice-profile.json` 至少记录模型标识、模型版本或 revision、语言、参考 WAV 路径、准确逐字稿和参考 WAV SHA-256。
- Read Along 与 sidecar 都读取该档案，但缓存指纹由 Read Along 从本地配置和文件内容计算，不依赖 sidecar 在线。

## Sidecar 与应用边界

- 重型模型运行在独立进程中，只绑定 `127.0.0.1`，不嵌入 Read Along 主进程，也不监听局域网地址。
- `GET /health` 返回就绪状态、模型标识、模型版本和声音档案摘要。
- `POST /v1/speech` 接收句子原文和声音档案摘要，摘要匹配时返回 WAV；不匹配时明确拒绝，避免缓存身份与实际声音漂移。
- Read Along 新增显式后端名 `local_clone_tts`，通过配置指定 sidecar 地址和声音档案路径。
- 缓存指纹包含句子原文、后端名、模型及版本、合成参数、声音档案内容和参考 WAV SHA-256。
- sidecar 停止时，材料库仍可返回已有的匹配缓存；需要生成新音频时明确失败并允许重试，不自动切换 Kokoro。
- 服务未启动、模型未就绪、请求超时、档案摘要不匹配或输出无效时，删除本次不完整输出并返回可诊断错误。

## 关键决策

- 先评测后集成，评测结果不预设胜者。
- 质量优先，但合格模型必须在目标机器上预热后持续生成速度不慢于播放速度。
- 第一版只维护一个全局参考声音，不增加声音选择 UI。
- Kokoro 保留为用户显式选择的轻量后端，不作为运行时自动降级。
- Apple Silicon 支持以目标机器实测为准，不以 CUDA 路径的官方性能数据推断。
- 只有胜出模型进入稳定 sidecar；另一个模型的环境和依赖不进入产品运行路径。

## Topic 级验证

- 两个候选模型的评测记录包含环境、revision、参数、自动指标、稳定性结果和匿名盲测映射。
- 在目标 M4、16GB MacBook Pro 上完成冷启动、首句、预热后 RTF、峰值内存和至少 20 句连续生成验证。
- 若有胜者，验证 sidecar 只监听 `127.0.0.1`，健康检查和合成协议符合约定，声音档案摘要不匹配会被拒绝。
- 若有胜者，测试覆盖配置加载、缓存指纹、匹配缓存离线复用、超时、无效输出、不完整文件清理和禁止自动降级。
- 若无胜者，确认主应用实现和默认后端保持不变，并记录淘汰证据。
- 运行 `make check`；涉及真实 sidecar 的路径另做目标机器集成验证，不要求 CI 下载重型模型。
